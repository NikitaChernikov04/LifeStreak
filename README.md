# 🔥 LifeStreak

> «Стань человеком, которым всегда хотел быть.»

Telegram Mini App, превращающая жизнь пользователя в коллекцию красивых непрерывных серий (streaks). MVP отвечает на один вопрос: **вернутся ли пользователи завтра, чтобы не потерять серию?**

## Быстрый старт (Docker)

```bash
cp .env.example .env      # заполните JWT_SECRET, TELEGRAM_BOT_TOKEN и обе строки БД
docker compose up --build
```

- Backend API: http://localhost:3000/api/v1
- Frontend: http://localhost:5173

Postgres в compose нет намеренно: база живёт в Supabase, и локальный контейнер
с другим Postgres проверял бы не ту базу, на которой всё работает. При каждом
старте контейнер прогоняет `prisma migrate deploy` и сид каталогов (достижения
и шаблоны испытаний) — обе операции идемпотентны. Чтобы получить ещё и
демо-пользователя с примерами серий, поставьте `SEED_DEMO=true` в `.env`.

## Локальная разработка без Docker

Нужен **отдельный проект Supabase для разработки** — второй, не боевой.
Бесплатный тариф даёт ровно два, и это как раз тот случай, ради которого
стоит потратить второй: гонять миграции и сид по базе живых пользователей
нечем оправдать.

### 1. Backend

```bash
cd backend
cp .env.example .env        # DATABASE_URL и DIRECT_URL — из dev-проекта Supabase
npm install
npm run db:migrate          # prisma migrate deploy
npm run prisma:seed         # SEED_DEMO=true в .env добавит демо-данные
npm run start:dev
```

> Разработка теперь требует сети. Это прямая плата за переезд: файловая
> SQLite поднималась из ничего и работала в самолёте, Postgres — нет.

Для локальной разработки без реального Telegram-бота оставьте
`TELEGRAM_SKIP_AUTH_VALIDATION=true` в `backend/.env` — фронтенд в браузере
(вне Telegram) будет логиниться демо-пользователем без проверки HMAC-подписи
`initData`. В продакшене эта переменная обязательно должна быть `false` —
при `NODE_ENV=production` бэкенд откажется стартовать, если она осталась
`true`, если пуст `TELEGRAM_BOT_TOKEN` или если `JWT_SECRET` короче 32
символов (см. `src/config/assert-production-config.ts`).

### 2. Frontend

```bash
cd frontend
cp .env.example .env
npm install
npm run dev
```

Откройте http://localhost:5173 — приложение работает и в обычном браузере
(эмулируя Telegram initData), и как полноценный Telegram Mini App.

Всё, что касается двух людей — подписки, заявки, реакции, — проверяется
двумя вкладками: `?devUser=Аня` и `?devUser=Боря` дают разные учётки с
устойчивыми id. Параметр читается только в браузерном fallback, который
работает лишь при `TELEGRAM_SKIP_AUTH_VALIDATION=true`.

## Социальный слой

Дружба **взаимная и всегда по заявке**: один просит, второй отвечает, и после
подтверждения строка читается одинаково с обеих сторон. `requesterId` и
`addresseeId` в `friendships` фиксируют, кто спросил, — они важны только пока
заявка висит.

Пара всегда одна. Уникальный индекс сам этого не гарантирует (A→B и B→A
прошли бы оба), поэтому сервис проверяет оба направления перед записью, а
встречную заявку трактует как согласие: второй запрос не создаёт строку, а
принимает первую. Отказ **удаляет** строку, а не хранит «нет», — попросить
можно снова. Это осознанно не блокировка.

Согласие двухуровневое, и второй уровень закрыт по умолчанию:

1. **Дружба.** Даёт право читать. Отдельный флаг `isDiscoverable` решает
   только то, находят ли человека поиском до этого разговора.
2. **Серия.** Принятая заявка не открывает каждую привычку: у серии свой
   `isShared`, по умолчанию выключенный. В ленту и в чужой профиль попадают
   только отмеченные серии.

Оба условия перечитываются на каждом запросе, а не записываются в отметку:
удаление из друзей или снятый флаг убирают из ленты и уже сделанные записи.
Реакция (одна на человека на отметку, переключается) требует того же
доступа, что и чтение, — на скрытую отметку сервер отвечает 403.

### Рейтинг

Считается среди друзей и себя, по самой длинной серии, которую человек ведёт
**прямо сейчас**. Число берётся по всем активным сериям, включая закрытые
флагом: соревнование именно на нём, а голая цифра говорит «сколько», но
никогда «что» — названия остаются за флагом. Ничьи делят место, следующее
пропускается: за двумя первыми идёт третий.

По той же причине в чужом профиле `activeStreaksCount` подменяется числом
видимых серий. Настоящее значение позволило бы вычесть и узнать, сколько
серий от тебя скрыли, — тот самый вывод, который профиль намеренно не даёт.

### Общие цели

Цель держат несколько друзей. День засчитывается **группе**, только когда
отметились все вступившие, — `currentCount` принадлежит группе, а не сумме
чьих-то усилий. Приглашение не участие: цель не ждёт того, кто не согласился.

Состояние выводится из `lastCountedDate`, а не поддерживается планировщиком:
крона в проде нет, поэтому цель, «сорвавшаяся» ночью, обязана прочитаться
сорванной при первом открытии. Сервис сверяет дату с сегодняшней на каждом
чтении и сохраняет найденный обрыв.

Окно — два дня, а не один: если последний зачтённый день позавчерашний, то
вчера пропущено, но его ещё можно выкупить сердцем, и обнулять счёт сразу
значит сделать спасение недостижимым. Ещё сутки без полного состава — счёт в
ноль. То же окно, что у личной серии.

Закрытый день продлевает цепочку, только если стоит сразу за предыдущим.
Закрыть сегодня при открытом вчера — не продление, а новый отсчёт с единицы:
иначе пропуск бесшумно замазывался бы.

Обрыв не наказывают. Обнулённый счёт и так последствие, а штраф в сердцах дал
бы способ расплатиться и перестать это чувствовать. Наоборот: тот, кто свой
день в сорвавшихся сутках закрыл, получает за него сердце
(`GROUP_GOAL_HELD`) — заработанная часть возвращается, потерянная нет.

### Спор

Второй режим той же сущности (`GroupGoal.mode = "VERSUS"`). Общая цель — один
счёт на всех; спор — у каждого свой, и считают их **не одной суммой за всё
время, а спринтами**.

Сумма не работает: как только между людьми открывается настоящий разрыв,
догнать первого нельзя в принципе, и отставший становится зрителем на всю
оставшуюся дистанцию. Спринт начинается заново, поэтому проиграть можно четыре
спринта, а не двадцать дней, и следующий всегда отыгрывается. Длина спора
поэтому задаётся не днями, а числом спринтов: `targetDays = sprintDays ×
sprintCount`, и последний спринт никогда не выходит короче остальных.

Спринт берёт тот, у кого в нём больше отмеченных дней, и **никто**, если
поровну: выиграть у друга по умолчанию — не выигрыш. Отдельно считается
«чистый спринт» — когда все отметили все дни. Это лучший исход, какой у
спринта есть, и он же ничья; засчитывать его как «никто не выиграл» значило бы
тихо желать другу сорваться.

Спринты, которые уже шли, когда человек вступил, ему не в минус — отрезок, в
котором его не было, не может быть против него.

Считается лениво, как и обрыв общей цели: крона нет, поэтому спринт,
закончившийся ночью, закрывается при первом чтении. `settledSprint` — то, что
не даёт объявить один и тот же спринт дважды.

Выкупить прошлый день сердцем в споре нельзя: это была бы покупка очка у
соперника, а спасение существует, чтобы один участник мог вытащить группу.

**Пруфы.** К любому дню можно приложить строку, ссылку и фото. Это
свидетельство, а не пропуск: никто их не подтверждает, на счёт они не влияют,
день без пруфа считается ровно так же. Подтверждение вторым участником
означало бы блокирующий шаг на единственном действии, которое обязано быть
мгновенным, и всё равно не остановило бы того, кто решил соврать.
Останавливает другое: пруф читает ровно тот человек, который знает, врёшь ты
или нет. Поэтому пруфы отдаются **только участникам этого спора** и больше
нигде в API не появляются — ни в ленте, ни в сводке бота.

Фото сжимается **в браузере**, до отправки: длинная сторона до 1600 px,
короткая не ниже 720 (иначе высокий скриншот телефона ужимается до нечитаемой
ширины), WebP с откатом на JPEG, качество ступенями вниз, пока файл не влезет
в 320 КБ. Скрин коммита 1800×1240 выходит 61 КБ и читается целиком; скрин
приложения 780×2556 — 77 КБ.

Хранится всё в **приватном** Vercel Blob (`BLOB_READ_WRITE_TOKEN`). В базе
лежит только pathname, никогда не URL, и наружу он не отдаётся: клиент узнаёт
лишь `hasImage`. Байты идут через `GET
/social/goals/:id/proofs/:checkinId/image`, который на каждый запрос
проверяет, что человек `JOINED` в этой цели. Публичный стор дал бы
CDN-адрес, работающий у любого, кто держит строку, — и «видят только
участники» превратилось бы в «ссылку никто не переслал». Цена решения в том,
что фото нельзя подставить в `<img src>`: фронтенд забирает его запросом с
токеном и отдаёт тегу object URL.

Загрузка ограничена 2 МБ и тремя MIME-типами, которые холст умеет выдать.
Это заслон против клиента, который ничего не сжал, а не ожидаемый размер.

Фото открывается на весь экран и вписывается **по ширине**, а не целиком:
скрин телефона вчетверо выше экрана, и «показать целиком» превращает его в
полоску в 174 px — ровно ту деталь, ради которой окно и нужно. Второе нажатие
даёт натуральный размер с прокруткой.

**Прошлые дни.** Карточка несёт только свежие пруфы; всё остальное — за
кнопкой «прошлые дни». История читается **по одному дню**: сперва день
выбирается из списка (`GET …/proof-days` — даты, спринт и число записей),
потом читается карточками (`GET …/proofs?date=`). Бесконечная лента здесь
была бы неверной формой — на споре в сто дней это две сотни записей, а нужна
всегда конкретная. Побочный выигрыш в том, что грузятся фотографии только
открытого дня.

Чтение фото ретраится дважды: байты идут из хранилища по сети, и этот участок
падает на плохой связи. Одна осечка без ретрая оставляла бы «не открылось»
навсегда, поэтому там же есть кнопка «повторить», а недоступность хранилища
на бэкенде превращается в 503, а не в необработанное исключение.

**Финал.** Цель можно объявить выполненной, не досчитав до `targetDays`:
`POST /social/goals/:id/complete`. Это может **любой вступивший**, не только
владелец, — цель это обещание друг другу, и увидеть его сбывшимся может любая
сторона; ставить кого-то одного в позицию выдающего разрешение не за что.
Отдельная кнопка от «бросить цель»: та закрывает цель как брошенную
(`ABANDONED`), эта — как сдержанную (`COMPLETED`), и сердце получают все.

## Что бот говорит вслух

Приложение живёт в Telegram, значит у него есть то, чего нет у обычного
трекера: канал, который человек и так читает каждый день. Это преимущество
тратится ровно один раз — приложение, которое пишет по любому поводу, получает
«Отключить уведомления», и после этого сказать ему больше нечего.

Отсюда правило в одну строку: **уведомление получает сообщение, только если
человек не мог его увидеть сам.** Сердце, уровень, награда, закрытый общий
день — всё это происходит, когда пользователь смотрит на экран, и дублировать
это в чат незачем. Остаются чужие действия: заявки, реакции, приглашения — и
два факта, которые нельзя узнать поздно: цель сорвалась и цель взята.

Список живёт в `DELIVERED` (`notification-delivery.service.ts`), рядом с тремя
ограничителями:

- **всплески** — реакции сворачиваются в одно сообщение на три часа, вступления
  в цель — на час; счёт идёт по `notifications.deliveredAt`, то есть по
  отправленному, а не по записанному, чтобы несделанная отправка не глушила
  следующую;
- **присутствие** — если `lastSeenAt` моложе трёх минут, человек, скорее всего,
  всё ещё в приложении, и телефон молчит;
- **закрытый чат** — Telegram отвечает `403` и на блокировку, и на «никогда не
  нажимал Запустить»; оба случая записываются в `users.botBlocked`, и больше мы
  туда не стучимся. Снимается это только из чата с ботом — поэтому вебхук
  слушает `/start` и `my_chat_member`, а профиль показывает подсказку со
  ссылкой.

Плюс `dmEnabled` — выключатель на «Профиле», после которого всё то же самое
остаётся внутри приложения.

### Вечерняя сводка

Единственное сообщение, которое бот начинает сам: `POST /api/v1/cron/digest`,
вызываемый Vercel Cron в 17:00 UTC (20:00 по Москве, всё ещё внутри тех же
UTC-суток, в которых считаются дни).

Одно сообщение на человека, а не по одному на серию. Порядок строк — по силе:
цель, где ждут **только тебя**, идёт первой, потом цель под угрозой обрыва,
потом список неотмеченных серий. Повторный запуск за те же сутки не шлёт
ничего: признак — уже созданное сегодня уведомление `STREAK_REMINDER`, так что
идемпотентность не зависит от того, сколько раз сработал планировщик.

### Круги в групповых чатах

Любому трекеру, который хочет социального давления, сначала нужно построить
круг близких людей — и почти никто его не достраивает. Групповой чат в Telegram
это круг, который уже существует: люди, имена и привычка читать его каждый день
на месте до нашего появления. Это единственное, чего трекер из App Store не
может структурно.

Бота добавляют в чат, участники пишут там `/join`, и каждый вечер туда уходит
одна строка:

```
Вечерняя сверка

✓ Аня — 3 из 3
· Борис — 1 из 2
· Вера — 0 из 2
```

Закрывшие идут первыми, отставший — последним: список читают сверху вниз, и тот,
кому он адресован, оказывается там, где взгляд останавливается. Если закрыли
все, строка одна и другая.

**Что чат не узнаёт — что именно вы отмечаете.** `Streak.isShared` это согласие
быть прочитанным *друзьями*, а групповой чат — другая аудитория; переиспользовать
флаг значило бы протечь одно в другое. Наружу идёт только счёт, а согласие —
само вступление, отзываемое через `/leave` или кнопкой «Выйти» в профиле, тихо и
без объявления в чат.

Команды (`chat-circle.service.ts`) работают только внутри группы: возможность
писать в чат и есть доказательство принадлежности к нему, другого у нас нет.

| | |
|---|---|
| `/join` | попасть в список |
| `/leave` | выйти из него |
| `/status` | посмотреть, как дела сейчас |
| `/help` | то же, что бот пишет при добавлении |

Режим приватности бота (BotFather → Group Privacy) **оставляйте включённым** —
тогда до нас доходят только команды, а не переписка. Круг меньше двух человек
вечером молчит: строка в чате, адресованная одному, это не сверка. Чат, из
которого бота удалили, гасится по `my_chat_member`; чат, ответивший `403`, гасит
себя сам при следующей сверке, никого при этом не помечая заблокировавшим бота.

Фронтенд и API живут **в одном проекте Vercel**, база — в **Supabase**
(PostgreSQL as a service). Ни один из сервисов не требует карты.

Боевой адрес: **https://lifestreak.vercel.app**

### Как это устроено

`vercel.json` описывает две сборки под одним доменом:

```
frontend/package.json  → @vercel/static-build, Vite-статика из dist/
backend/api/index.js   → @vercel/node, serverless-функция
routes                 → /api/* в функцию, статика по файлам, остальное в index.html
```

Один домен означает, что CORS не участвует вовсе, а фронтенд обращается к
относительному `/api/v1` (см. `frontend/src/lib/api.ts`, где это же значение —
дефолт для любой не-dev сборки).

### Функция обязана жить в одном регионе с базой

`"regions": ["fra1"]` в `vercel.json` — не тонкая настройка, а условие
работоспособности. По умолчанию Vercel ставит функцию в `iad1` (Вашингтон),
база — в `eu-central-1` (Франкфурт), и каждый запрос к БД летит через Атлантику.

Замер по `/api/v1/health`, который сам сообщает `dbMs`:

| | круговой запрос к БД | отметка дня (было 19 запросов) |
|---|---|---|
| `iad1` → Франкфурт | ~90–100 мс | ~1.8 с |
| `fra1` → Франкфурт | 11–20 мс | ~250 мс |

Ключевая мысль: **запрос стоит один сетевой перелёт независимо от того, что он
выбирает.** Поэтому ожидание пользователя — это время перелёта, умноженное на
то, сколько раз код спросил отдельно то, что мог спросить вместе. Отсюда оба
правила: держать функцию рядом с базой и не выстраивать запросы в цепочку без
нужды.

Проверять после каждого деплоя: `vercel inspect <url>` печатает регион рядом с
функцией — `λ backend/api/index.js [fra1]`.

**Почему точка входа — обычный JavaScript.** `backend/api/index.js` не
компилируется, а только реэкспортирует результат `nest build`:

```js
module.exports = require('../dist/serverless').default;
```

Vercel собирает файлы в `api/` сам, через esbuild, а тот не умеет
`emitDecoratorMetadata` — без неё Nest не резолвит конструкторы, и DI падает.
Поэтому TypeScript компилирует `tsc` (скрипт `vercel-build`), а шим только
передаёт готовый обработчик.

`src/serverless.ts` кэширует **промис** загрузки, а не приложение: на холодном
старте несколько параллельных запросов ждут одну инициализацию вместо трёх.
Общая настройка Nest вынесена в `src/app.setup.ts` — её делят обычный сервер
(`main.ts`, локально и в Docker) и функция, чтобы расхождение между ними не
всплыло только в проде.

> Раньше проект жил на альфа-режиме `services`. Его пришлось убрать: формат
> ломался при каждой смене версии Vercel CLI на билд-машине, а на CLI 58
> перестал собирать бэкенд с рабочими зависимостями вообще.

### 1. База данных в Supabase

Создайте проект на [supabase.com](https://supabase.com). В **Connect** есть
две строки подключения, и путать их нельзя:

| | порт | параметры | кто использует |
|---|---|---|---|
| `DATABASE_URL` | `6543` (transaction pooler) | `pgbouncer=true&connection_limit=1&connect_timeout=15` | приложение |
| `DIRECT_URL` | `5432` (session) | `connect_timeout=15&connection_limit=1&pool_timeout=30` | `prisma migrate`, сид, импорт |

Каждый запрос обслуживает отдельный вызов serverless-функции, и функция,
открывающая собственное соединение с Postgres, исчерпает сервер задолго до
процессора. Пулер выдаёт соединение на транзакцию, а не на клиента — только
такая форма это переживает. Миграции наоборот берут advisory-локи и гоняют
DDL, чего через транзакционный пулер сделать нельзя, поэтому им нужен `5432`.

Хвосты у обеих строк — не перестраховка, а два измеренных отказа:

- **`connect_timeout=15`.** TCP до пулера отвечает за 1 мс, а рукопожатие
  Postgres занимает 2–3.5 секунды при дефолте Prisma в 5. С дефолтом
  соединения рвались в 8 случаях из 10, и выглядело это как «база недоступна»
  при полностью открытом порте.
- **`connection_limit=1` на `DIRECT_URL`.** Без него Prisma открывает по
  соединению на ядро (здесь тринадцать) к сессионному пулеру, которому столько
  не нужно, и скрипт падает с `P2024` ещё до первого запроса.

Схему и справочные данные — обе команды идемпотентны:

```bash
cd backend
DATABASE_URL="postgresql://...6543/postgres?pgbouncer=true&connection_limit=1" \
DIRECT_URL="postgresql://...5432/postgres" npm run db:migrate
DIRECT_URL="postgresql://...5432/postgres" npm run prisma:seed
```

**Перенос старой базы Turso** (разовый, `scripts/import-from-turso.mjs`):

```bash
TURSO_DATABASE_URL="libsql://..." TURSO_AUTH_TOKEN="..." \
DIRECT_URL="postgresql://...5432/postgres" npm run db:import
```

Строки идут как есть, в порядке внешних ключей, с сохранением исходных cuid —
иначе развалились бы все ссылки. Переводятся только типы, которых у SQLite
нет: булевы `0/1` и даты, лежащие там ISO-строками. Скрипт отказывается
работать по непустой базе и в конце сверяет число строк в каждой таблице —
молчаливый успех у такого скрипта не стоит ничего.

> `@libsql/client` остался в `devDependencies` ровно ради этого скрипта. Когда
> перенос сделан и старая база больше не нужна — зависимость и скрипт можно
> удалить одним коммитом.

### 2. Проект на Vercel

```bash
npx vercel login
npx vercel link --yes --project lifestreak
npx vercel --prod
```

Переменные окружения (Production):

| Переменная | Значение |
|---|---|
| `DATABASE_URL` | строка пулера Supabase, `:6543`, с `?pgbouncer=true&connection_limit=1` |
| `DIRECT_URL` | строка сессии Supabase, `:5432` — только для миграций |
| `JWT_SECRET` | случайная строка от 32 символов |
| `TELEGRAM_BOT_TOKEN` | токен от @BotFather |
| `TELEGRAM_SKIP_AUTH_VALIDATION` | `false` |
| `TELEGRAM_MINIAPP_SHORT_NAME` | короткое имя из `/newapp` — нужно для ссылок-приглашений |
| `TELEGRAM_BOT_USERNAME` | необязательно; пустое значение подтягивается через `getMe` |
| `TELEGRAM_WEBHOOK_SECRET` | случайная строка; без неё вебхук отвечает 403 на всё |
| `CRON_SECRET` | случайная строка; без неё вечерняя сводка не запускается |
| `DEMO_LOGIN_SECRET` | ключ демо-входа; пустое значение закрывает его наглухо (см. «Демо для записи») |
| `BLOB_READ_WRITE_TOKEN` | ставится сам при `vercel blob create-store <имя> --access private`; без него фото к пруфам не принимаются |
| `VITE_API_URL` | `/api/v1` |

Оба секрета работают как рубильники: пока значение не задано, соответствующий
эндпоинт закрыт наглухо, а не открыт всем. Это сделано намеренно — забытая
переменная должна выключать функцию, а не публиковать её.

Проверка после деплоя:

```bash
curl https://lifestreak.vercel.app/api/v1/health
```

> **Prisma и кэш зависимостей.** Vercel восстанавливает `node_modules` из
> кэша, не повторяя генерацию клиента, поэтому в `backend/package.json` есть
> `postinstall: prisma generate`. Без него бэкенд падает на старте с
> `PrismaClientInitializationError`.

> **Миграции — вручную, до деплоя.** Автоматического хука нет намеренно:
> миграция по боевой базе не должна зависеть от того, дособрался ли билд.
> Меняли схему — сначала `npm run db:migrate` по проду, потом пуш, иначе
> новый код придёт на старую схему. Команда идемпотентна, лишний запуск
> ничего не сломает.

### Демо для записи

Показывать продукт на живых записях своих друзей нельзя, поэтому есть
выдуманный мир: `backend/scripts/seed-demo-world.ts` заводит героя и семь
человек вокруг него — серии во всех состояниях, две общие цели, два спора
(один ведём, второй проигрываем), пять друзей, две заявки, награды, задание
дня.

```bash
cd backend
DIRECT_URL="postgresql://...5432/postgres" npx ts-node scripts/seed-demo-world.ts
```

Повторный запуск пересобирает мир заново — дубль записи должен начинаться с
того же кадра.

Вход — `POST /auth/demo` с ключом из `DEMO_LOGIN_SECRET`, а в приложении он
приходит стартовым параметром мини-аппа:

```
https://t.me/<бот>/<короткое имя>?startapp=demo_<ключ>
```

Так демо открывается **настоящим приложением внутри Telegram**, а не страницей
в браузере — иначе запись показывала бы не тот продукт. В профиле демо-сессия
подписана и выходится одной кнопкой.

**Почему эта дверь безопасна**, а не «просто вход в обход Telegram»:

- Пустой `DEMO_LOGIN_SECRET` закрывает её наглухо — забытая переменная
  выключает функцию, а не открывает её всем.
- Эндпоинт не принимает имени пользователя. Он умеет выдать сессию **только**
  для `demo-hero`, так что указать его на живого человека нечем.
- `demo-hero` не может совпасть ни с одним аккаунтом: Telegram id числовой.
- Ключ сверяется за постоянное время и throttle сбит до 5 попыток в минуту.
- Худшее, что даёт утёкший ключ, — посмотреть на выдуманных людей.

Выдуманные люди не засоряют боевое приложение: рейтинг считается по друзьям
смотрящего, поиск фильтрует по `isDiscoverable` (у них `false`), а `dmEnabled:
false` гарантирует, что бот никогда не попытается им написать.

> **Бесплатный Supabase засыпает через неделю без запросов.** Проект не
> удаляется, но перестаёт отвечать до ручного запуска из панели. Здесь это
> покрыто само собой: крон `/api/v1/cron/digest` ходит в базу каждый вечер,
> так что неделя тишины физически не наступает. Если крон когда-нибудь
> выключат — это первое, что сломается, и сломается молча.

> **Проверять деплой до промоушена.** `npx vercel deploy --prod --skip-domain`
> собирает с боевыми переменными, но не переключает домен; после проверки —
> `npx vercel promote <url>`. Откат тем же `promote` на предыдущий деплой
> занимает секунды. Учтите, что на непромоутнутом URL включена защита
> деплоя: GET через `vercel curl` проходит, а POST она отбивает голым
> `400 Bad Request` — это не приложение.

### 3. Подключение к боту

В [@BotFather](https://t.me/BotFather):

1. `/newapp` → выберите бота → название, описание, иконка 640×360.
2. **Web App URL**: `https://lifestreak.vercel.app`
3. Короткое имя (short name), которое спросит `/newapp`, положите в
   `TELEGRAM_MINIAPP_SHORT_NAME` — из него собираются ссылки-приглашения
   `https://t.me/<bot>/<short-name>?startapp=<code>`. В проде это
   `Life_Streakbot` и `start`, то есть `https://t.me/Life_Streakbot/start`.
4. `/setmenubutton` → тот же URL → подпись кнопки (например, «Открыть журнал»).
5. Вебхук — чтобы бот узнавал о нажатом «Запустить»:

```bash
curl -X POST "https://api.telegram.org/bot<TOKEN>/setWebhook" \
  -H 'content-type: application/json' \
  -d '{"url":"https://lifestreak.vercel.app/api/v1/telegram/webhook",
       "secret_token":"<TELEGRAM_WEBHOOK_SECRET>",
       "allowed_updates":["message","my_chat_member"]}'
```

Telegram присылает секрет обратно в заголовке `X-Telegram-Bot-Api-Secret-Token`,
и всё, что приходит без него, отбрасывается. `allowed_updates` сужен до двух
типов сознательно: остальное боту не нужно, а каждый лишний тип — это трафик
и лишний путь внутрь.

> В обычном браузере продакшен входить **не будет**, и это правильно:
> `TELEGRAM_SKIP_AUTH_VALIDATION=false` включает проверку HMAC-подписи, а у
> браузерного fallback подписи нет. Вместо приложения показывается экран
> «Вход не выполнен».

### Холодный старт

Бэкенд-сервис засыпает при простое; первый запрос поднимает Nest заново
(порядка 1–2 секунд), дальше ответы быстрые.

## Игровая механика (кратко)

| Механика | Правило |
|---|---|
| Отметка дня | +20 XP, серия +1 день |
| Пропуск 1 дня | можно восстановить одним ❤️ (только последний пропуск) |
| Пропуск 2+ дней | серия сбрасывается до 1 |
| Серия кратна 7 | +1 ❤️ (максимум 5, старт — 3) |
| Испытание дня | случайное каждый день, +40 XP или ❤️ |
| Уровень | 500 XP на уровень, чисто визуальная награда |
| Приглашение друга | +1 ❤️ обоим при принятии кода |
| Перенос серии | при создании можно указать уже накопленные дни (см. ниже) |
| Достижения | 7/30/100/365 дней, первое сердце, первое восстановление, без пропусков, коллекционер (5 серий), легенда (20 уровень) |

### Перенос уже накопленных дней

Люди приходят с историей: сто дней без сигарет, посчитанные в другом
трекере. При создании серии поле «Уже идёт» (`startingCount`, до 3650)
переносит эти дни: они ложатся в `currentCount` и `longestCount`, дублируются
в `importedCount` и датируются вчерашним днём — сегодняшний пользователь
отмечает сам, потому что именно эта привычка и строится.

Перенесённые дни не приносят XP, сердец и достижений: их зарабатывают
в журнале, а не объявляют на входе. На ленте записи они нарисованы пустыми
клетками — видно, где чужая история, а где своя.

### Приглашения

Приглашение — это ссылка, а не код. `GET /invites/me` возвращает код вместе
с готовым `https://t.me/<bot>/<app>?startapp=<code>`; друг, открывший её,
попадает в приложение с кодом в `start_param`, и фронтенд принимает его сам
(`useRedeemInviteFromLink`). Код остаётся видимым как запасной путь — его
можно ввести вручную в профиле. Сердце получают обе стороны.

## API

Полный REST API под префиксом `/api/v1`, версионирование через
`VersioningType.URI`. Основные группы:

- `POST /auth/telegram` — вход по `initData`
- `GET/POST /streaks`, `POST /streaks/:id/checkin`, `POST /streaks/:id/recover`
- `GET /challenges/today`, `POST /challenges/:id/complete`
- `GET /achievements`, `GET /achievements/me`
- `GET /hearts`
- `GET /statistics/me`
- `GET /invites/me`, `POST /invites/accept`
- `GET /notifications`, `GET/PATCH /notifications/settings`
- `GET/POST /social/goals`, `POST /social/goals/:id/{join,checkin,rescue,complete}`
  — общие цели и споры, `POST …/checkin` принимает необязательный пруф
- `POST /social/goals/:id/proof` — фото к сегодняшнему дню (multipart, `image`)
- `GET /social/goals/:id/proof-days` — дни, за которые есть пруфы
- `GET /social/goals/:id/proofs?date=` — пруфы, при желании за один день
- `GET /social/goals/:id/proofs/:checkinId/image` — байты фото, только участникам
- `GET /circles`, `DELETE /circles/:id` — групповые чаты, где тебя считают
- `GET /health` — проба для хостинга

Публичных роутов четыре, и три из них закрыты не JWT, а секретом:

- `POST /auth/telegram` — вход
- `GET /health` — проба хостинга
- `POST /telegram/webhook` — только с `X-Telegram-Bot-Api-Secret-Token`
- `GET|POST /cron/digest` — только с `CRON_SECRET` (Vercel шлёт его как
  `Authorization: Bearer`)

Все защищённые роуты требуют `Authorization: Bearer <JWT>`, полученный из
`/auth/telegram`. Ответы оборачиваются в `{ success, data }`; ошибки — в
`{ success: false, statusCode, message }`.

## Дизайн — «Журнал наблюдений»

Интерфейс устроен как лабораторный журнал, который пользователь ведёт на
себя: тёплая бумага в клетку, записи, отделённые линейками, вместо
карточек-плашек. Страница идёт во всю ширину — на экране в 320 пикселей
поле-гутер съедало шестую часть строки, а записи и так читаются как
разлинованный лист.

**Палитра** (CSS-переменные в `frontend/src/index.css`):

| Токен | Значение | Роль |
|---|---|---|
| `--paper` | `46 38% 93%` | бумага — тёплый крем состаренной тетради |
| `--ink` | `30 14% 13%` | чернила: тёплый чёрный, нейтральный на креме синит |
| `--graphite` | `38 9% 45%` | карандаш, вторичный текст |
| `--indigo` | `205 28% 28%` | активное состояние, каретка сегодняшнего дня |
| `--vermilion` | `9 58% 47%` | **только** разрывы серии и восстановление |
| `--ochre` | `33 48% 44%` | всё заработанное: сердца, награды, дни с сердцем |

Дисциплина цвета: киноварь не используется как акцент — она означает
пропуск. Всё, что пользователь заработал, окрашено охрой. Цвета самих
серий — приглушённые пигменты (`STREAK_TEMPLATES` в бэкенде и `COLORS` в
`CreateStreakDialog`), они появляются один раз, на плитке записи.

**Типографика**: `PT Sans Narrow` (дисплей, капс с трекингом — кириллица от
ParaType), `IBM Plex Mono` (даты, счётчики, подписи полей), `IBM Plex Sans`
(проза). Все три подключены через `@fontsource` с кириллическими сабсетами.

**Сигнатурный элемент** — `RecordTape` (`components/streaks/RecordTape.tsx`):
серия как лента записи шириной в две недели, где форма кодирует правила
игры, а не украшает их — залитая клетка это записанный день, охряная — день,
принёсший сердце (каждый 7-й), пустая с рамкой — день, перенесённый из
прежнего трекера, пунктирная мигающая — сегодня, ещё не записанный,
киноварная — пропуск.

Анимация ограничена тремя местами: появление записей, «штамп» при отметке дня
и печать награды в `CelebrationOverlay`. `prefers-reduced-motion` отключает
всё это. Экспорт вырезки в PNG — через `html-to-image`.
